# Архитектура doh-finder

Основа — архитектурное руководство casino-go, переданное пользователем
(локальный файл `docs/architecture_guidelines.md`).
Для doh-finder сохраняются разделение слоёв и интерфейсы у потребителей.
По решению пользователя Uber Fx и Zap не применяются.

## Структура

```text
cmd/doh-finder/main.go                    точка входа, завершение по Ctrl+C
configs/servers.json                     генерируемый публичный DoH-каталог
internal/app/app.go                       флаги CLI и сборка зависимостей
internal/cli/                            консольное меню, вызов сценария и вывод
internal/pkg/ds/                         структуры каталога и резолверов
internal/service/catalog/                сценарий обновления, порты зависимостей
internal/service/check/                  пул горутин и сбор отчёта проверки
internal/service/browse/                 очередь, подтверждение и транзакция смены DNS
internal/platform/systemdns/             Windows DNS/DoH и проверка системного резолвинга
internal/platform/console/               очистка консоли с поддержкой Windows VT
internal/network/doh/                    TCP и DoH через AdGuard upstream
internal/source/dnscrypt/                HTTP-загрузка и разбор DNS stamps
internal/model/repository/jsonfile/      запись каталога в JSON
```

## Правила

1. Бизнес-логика находится в `internal/service`. Сервис импортирует только
   стандартную библиотеку и `internal/pkg/ds`.
2. Интерфейсы объявляются у потребителя в `deps.go`: сервису нужны `Source`
   и `Repository`, CLI — `CatalogService`.
3. Конструкторы возвращают конкретные указатели. Сопоставление реализаций с
   интерфейсами выполняется в `internal/app` обычными вызовами конструкторов.
4. Модели в `ds` используют базовые типы Go. Библиотечные структуры DNS stamps
   преобразуются в модели внутри адаптера источника.
5. HTTP, DNS stamps и файловая система не проникают в сервис. Проверки
   выполняются через порт `Prober`, реализованный сетевым адаптером.
6. Логирование — стандартный `log/slog`, логгер передаётся конструктору CLI.
   Ошибки адаптеров оборачиваются через `fmt.Errorf("context: %w", err)`;
   итоговая ошибка выводится на уровне приложения.
7. Сетевая работа принимает `context.Context`; таймауты и остановка по сигналу
   управляются точкой сборки. Консольное меню не ограничено таймаутом; для каждого
   обновления создаётся отдельный контекст с таймаутом. Ввод читается отдельно,
   чтобы Ctrl+C завершал программу при ожидании Enter.
8. Тесты HTTP-адаптера используют `httptest`; тесты записи — `t.TempDir`.
   Ошибки источника не должны приводить к перезаписи существующего каталога.
9. Используется только IPv4. Сервис каталога исключает IPv6-адреса подключения,
   IPv6-литералы в DoH URL и IPv6 bootstrap DNS. Записи без IP исключаются:
   каждая запись итогового JSON должна иметь явный IPv4-адрес из источника.
   Сетевой адаптер использует этот адрес для DoH. IPv6 fallback
   запрещён. Исходный stamp хранится для связи с источником; его bootstrap-адреса
   не должны обходить IPv4-политику через библиотечный клиент.

## Поток обновления

CLI → сервис каталога → адаптер DNSCrypt → сервис каталога → JSON-репозиторий.

Адаптер получает SHA актуального commit и загружает исходный файл по этому SHA.
Он преобразует все stamps с протоколом DoH в отдельные записи, добавляет сведения
об источнике. Сервис применяет IPv4-фильтр, проверяет непустой результат и
сортирует записи.
Репозиторий сначала записывает готовый JSON во временный файл рядом с целевым.
CLI сообщает число импортированных адресов после успешной записи.
По умолчанию открывается меню: `1. Update Server List`, `2. Check Servers`,
`3. Auto Browse`, `4. Full Cycle`, `0. Exit`. Каждый экран очищается; после операции возврат
в меню выполняется по Enter.
Флаг `-update` запускает одно обновление без меню для автоматизации.

## Поток проверки

CLI → сервис проверки → чтение JSON → пул горутин → сетевой адаптер → отчёт JSON.

`CatalogRepository`, `ReportRepository` и `Prober` объявлены у сервиса проверки.
Ограниченный пул получает задания через канал. Рабочие горутины отправляют
результаты в другой канал; единственный сборщик обновляет отчёт и вызывает
callback прогресса CLI. Индекс задания сохраняет порядок каталога в отчёте.
`WaitGroup` закрывает канал результатов после завершения всех работников.
Сборщик переносит признаки сервера из каталога в результаты и прогресс.
После завершения всех проверок в отчёте остаются только успешные серверы;
`checked` и `failed` сохраняют общие счётчики. Полный каталог не изменяется.

Адаптер параллельно проверяет TCP и два последовательных DNS A-запроса.
Для каждого DNS-запроса создаётся клиент AdGuard с одним IPv4 в `StaticResolver`.
TLS-сертификаты проверяются штатно, дополнительно проверяются хеши из каталога.
`upstream.Exchange` не принимает context: активный запрос ограничен таймаутом,
его завершение ожидается при отмене, фоновые сетевые задачи не оставляются.
Отмена останавливает выдачу новых заданий; неполный отчёт не сохраняется.
Отчёты в `reports/` являются результатами запуска и исключены из Git.

## Поток автоперебора

CLI → сервис browse → отчёт успешных серверов → сортировка по признакам и
среднему времени DoH → сохранённая очередь. При продолжении очередь не меняется.
`SystemDNS`, `StateRepository`, `ReportRepository` — порты у сервиса.

Перед применением сохраняется снимок адаптера в `state/browse.json`.
До подтверждения используется только основной сервер; резервного нет.
Системный адаптер использует `SetInterfaceDnsSettings` (IPv4 + DoH без fallback),
перечитывает результат и проверяет Windows DNS и HTTPS. DNS A-запрос привязан
к интерфейсу и обходит кэш/hosts; выполняется в дочернем процессе для жёсткого
ограничения времени. PowerShell только читает маршрут и метаданные адаптера.

Подтверждение добавляет предыдущий подтверждённый DNS резервным. При отказе,
отмене или выходе без подтверждения восстанавливается снимок. Откат использует
собственный контекст, чтобы Ctrl+C не отменил восстановление. Незаконченный
журнал восстанавливается при следующем запуске; при ошибке отката новые
серверы не применяются. Глобальный Windows mutex предотвращает два меню,
одновременно изменяющих DNS. Состояние в `state/` исключено из Git.

## Полный цикл

CLI → обновление каталога → базовая проверка → свежая отсортированная очередь
→ системная проверка до первого успеха. Пункт 4 выполняет те же сценарии и
сохраняет ручное подтверждение. `--full-cycle` работает без ввода: успешная
команда подтверждает выбранный сервер и добавляет предыдущий подтверждённый
как резервный. `--continue` ищет последний подтверждённый сервер в новой очереди
по IPv4 + DoH URL и продолжает после него; отсутствие такого сервера — ошибка
без применения новой сетевой конфигурации. `--browse --continue` использует
сохранённую очередь. Неуспешная или прерванная попытка откатывается через
тот же журнал, что и в пункте 3.
